# ADR-0007: 배포 전략

- 상태: **보류**
- 기록일: 2026-11-04

## 보류 이유

자원 사용량(특히 사용자 컨테이너의 실제 메모리)을 모르는 상태에서 서버 사양과 업체를 정할 수 없다. 로컬 개발과 Spike에서 측정한 뒤 결정한다.

## 지금까지 정리된 내용 (참고)

### 비용을 좌우하는 것은 RAM

웹 요청은 짧고 자원을 공유하지만, 터미널 실습은 유저마다 전용 컨테이너를 몇 분~수십 분 점유한다. 따라서 서버 비용은 "동시 실습 수 × 컨테이너 메모리"가 결정한다.

### 구성 단계안

| 단계 | 구성 | 특징 |
|---|---|---|
| 1 | 1대에 전부 (앱 + DB + runner) | 가장 저렴. 단, 사용자 셸과 DB가 같은 서버에 있음 |
| 2 | **2대: [앱 + DB] + [runner]** | 비용 대비 가장 효율적. 컨테이너 탈출 시 피해를 runner 서버로 한정 |
| 3 | 추가 분리 (웹 / API / DB) | 이 규모에서는 이득 대비 비용·운영 부담이 큼 |

### 업체 후보 (2026-11 조사 시점, 배포 직전에 재확인할 것)

| 후보 | 메모 |
|---|---|
| AWS EC2 | 인스턴스 외 공인 IPv4, EBS, 트래픽 비용 별도. T 계열 CPU 크레딧 초과 과금 주의. 여러 대로 나눌 때 NAT Gateway, AZ 간 전송 비용 주의. 학습·이력서 목적이면 의미 있음 |
| 일본 VPS (さくらのVPS 등) | 고정가, 예상 밖 청구 없음, 일본 리전 |
| Oracle Cloud Always Free | 0엔이지만 ARM, 무료 한도가 예고 없이 바뀐 이력, 유휴 계정 회수 위험. 검증용 |

### 어느 쪽을 택하든 지금 지킬 것

- docker-compose로 전체 실행 ([NFR-OPS-001](../../01-requirements/non-functional-requirements.md))
- amd64 / arm64 멀티 아키텍처 이미지 ([NFR-OPS-002](../../01-requirements/non-functional-requirements.md))
- 환경변수 기반 설정 ([NFR-OPS-003](../../01-requirements/non-functional-requirements.md))
- 서비스 간 경계(runner 분리, 네트워크 분리)를 로컬에서부터 유지

## 재검토 조건

- Spike 측정 결과가 나왔을 때
- MVP(Phase 3.5)가 로컬에서 동작할 때
