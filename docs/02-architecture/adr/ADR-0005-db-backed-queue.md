# ADR-0005: 실행 대기열은 PostgreSQL 테이블로 시작

- 상태: 확정
- 결정일: 2026-11-04

## 배경

저사양 서버 전제라 동시 실행 수를 제한해야 하고, 한도를 넘는 요청은 대기시켜야 한다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 메모리 큐 (애플리케이션 내부) | 가장 단순 | 서버 재시작 시 대기열 소실, 여러 인스턴스로 확장 불가 |
| B. PostgreSQL 테이블 + `SELECT ... FOR UPDATE SKIP LOCKED` | 추가 인프라 없음, 재시작해도 유지, 큐 동작 원리를 직접 학습 | 대량 트래픽에는 한계 |
| C. Redis / RabbitMQ | 큐 전용 기능, 대량 처리에 강함 | 인프라 하나 추가 (메모리, 운영 부담) |

## 결정

**B. PostgreSQL 테이블로 시작한다.**

워커는 다음 패턴으로 작업을 하나씩 가져간다.

```sql
SELECT * FROM execution_job
WHERE status = 'QUEUED'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

- `FOR UPDATE`: 가져간 행을 잠가서 다른 워커가 같은 작업을 처리하지 못하게 한다.
- `SKIP LOCKED`: 이미 잠긴 행은 기다리지 않고 건너뛴다. 여러 워커가 서로 막지 않고 동시에 일할 수 있다.

## 근거

- 저사양 서버에서 인프라를 하나라도 줄이는 것이 유리하다.
- 이 서비스의 대기열 규모(동시 수십 건 이하)에는 충분하다.
- 락, 중복 처리 방지, 실패 재시도 같은 큐의 핵심 개념을 직접 구현하며 배울 수 있다.

## 결과와 영향

- 입장 제어는 "동시 실행 개수"가 아니라 "실제 여유 메모리" 기준으로 한다 ([NFR-RES-003](../../01-requirements/non-functional-requirements.md)).
- 처리 도중 워커가 죽은 작업을 회수하는 로직이 필요하다 (`locked_at` 기준 타임아웃).
- 한계가 느껴지면 Redis 등으로 교체하고, 그 과정을 새 ADR로 남긴다.
