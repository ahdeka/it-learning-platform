# ADR-0004: 컨테이너 실행을 별도 runner 프로세스로 분리

- 상태: 확정
- 결정일: 2026-11-04

## 배경

사용자별 Docker 컨테이너를 만들고 지우려면 Docker Engine을 제어해야 한다. 보통 `/var/run/docker.sock`에 접근하는 방식인데, **이 소켓 접근 권한은 사실상 호스트의 root 권한과 같다.**

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. API 서버가 Docker를 직접 제어 | 구조 단순 | 외부 요청을 받는 서버가 root급 권한을 가짐. API 취약점 하나로 호스트 전체 탈취 가능 |
| B. 컨테이너 제어만 하는 runner 프로세스 분리 | 권한을 한 곳에 가둠. 나중에 runner만 다른 서버로 옮기기 쉬움 | 프로세스 간 통신이 생김, 구현량 증가 |

## 결정

**B. runner를 처음부터 별도 프로세스로 둔다.**

- runner만 `docker.sock`에 접근한다.
- runner는 DB에 접근하지 않는다.
- runner는 외부(브라우저)에서 직접 접근할 수 없고, backend에서만 호출한다.

## 근거

- 가장 위험한 권한을 가장 작은 범위에 가둔다 (최소 권한 원칙).
- 배포 시 "1대 구성 → runner만 별도 서버로 분리"가 이 프로젝트에서 가장 비용 대비 효과가 큰 분리이므로, 처음부터 그 경계를 코드 구조에 반영해 둔다.
- runner 서버의 CPU 폭주(사용자 무한 루프 등)가 웹과 DB에 영향을 주지 않게 분리할 수 있다.

## 결과와 영향

- 로컬에서도 docker-compose 네트워크로 runner와 DB를 분리한다.
- backend ↔ runner 통신 방식(HTTP + WebSocket / gRPC)은 Spike에서 결정한다.
- runner 자체가 뚫리는 경우에 대비한 추가 격리(rootless Docker, gVisor 등)는 Phase 2에서 검토한다.
